# 0006. Continuous integration

Status: accepted
Date: 2026-11-20

## Context
`build-sdm` can validate the data, check the generated output and run the tests, but nothing ran those checks on PRs. Illuminate had no CI covering the SDM at all. The checks need to run on every change to `main` without CI writing to the repo.

## Decision
- `.github/workflows/ci.yml` runs on every PR into `main`, on every push to `main`, and on demand. It has three jobs:
  - `data-lint`: `taplo fmt --check`, then `build-sdm validate --base-ref <base>`
  - `generated-fresh`: `build-sdm check-generated`
  - `python-qa`: ruff, ruff format, mypy and pytest
- Job names are stable, because required status checks select jobs by name. Renaming a required job blocks every PR until the ruleset names the new job.
- CI never commits. When the generated output is stale, the job fails and its summary shows the commands that fix it (ADR 0003).
- The base ref for `validate` (ADR 0004) depends on the event:
  - pull request: the PR's base branch
  - push: the commit before the push, so every pushed commit is covered. If there is none, or it's missing after a force push, compare against `HEAD` with a warning: with no base, every existing violation is an error and the job would always fail.
  - manual run: the merge base with `origin/main`, or `HEAD~1` when run on `main` itself
- A new push to a PR cancels that PR's previous run. Runs on `main` are never cancelled, because each validates only its own pushed range.
- Jobs run on GitHub-hosted `ubuntu-24.04` runners, not self-hosted ones, because the repo is public and accepts PRs from forks.
- Dependencies install with `uv sync --locked`, so a stale `uv.lock` fails instead of being re-resolved. Third-party actions are pinned to a major tag, or to an exact version where the action publishes no major tag (`astral-sh/setup-uv`).

## Consequences
- Every PR shows whether it adds a violation, leaves the generated output stale, or breaks the tool.
- A failing run doesn't block a merge until the jobs are made required checks; that is part of `docs/proposals/repo-governance.md`.
- Retargeting a PR to `main` doesn't start a run. `edited` isn't a trigger, because it also fires on every title and description edit, and filtering it with a job condition would produce skipped checks that count as passing.
- `validate` annotations name a file but no line, so they don't appear inline in the PR diff (follow-up F19).
