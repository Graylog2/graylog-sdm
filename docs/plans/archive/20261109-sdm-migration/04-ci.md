# SDM Migration — PR 4 of 5: PR CI workflow

Status: done
Tracking: https://github.com/Graylog2/graylog-sdm/pull/6

Overview: `docs/plans/sdm-migration/README.md`. Depends on PR 3 (`03-lint.md`). Next: `05-docs.md`.

## Context
Illuminate has no CI covering SDM data or build_gim. Its `ci.yml` lints only `tasks.py` and `illuminate_e2e`. This PR adds a GitHub Actions workflow to graylog-sdm that runs every check from PRs 2 and 3. Illuminate's `ci.yml` (uv + `invoke`) is a useful style reference, but don't copy its jobs.

## Decisions (from interview)
- Every PR runs: structural validation, codified rules (new violations fail), TOML formatting, generated-output freshness, and Python QA (ruff, mypy, pytest).
- If the committed `generated/MadcapHtmlOutput/` is stale, the PR fails. CI does **not** auto-commit; the contributor runs `build-sdm build` and commits the result.
- Python 3.13 only.

## Steps
1. Branch `migration/04-ci`.
2. `.github/workflows/ci.yml`:
   - `on: pull_request` (branches `[main]`), `push` (branches `[main]`), `workflow_dispatch`
   - `permissions: contents: read`
   - `concurrency`: grouped by ref for PRs, with cancel-in-progress; grouped by SHA on `main`, without it.
     Each push validates only its own commits (F6), so a cancelled run on `main` would leave a gap.
   - shared setup steps:
     - `actions/checkout@v7`; data-lint adds `fetch-depth: 0`, which the base ref needs
     - `astral-sh/setup-uv`, pinned to a version, with its default caching (on for PRs and pushes, off for events open to cache poisoning)
     - `uv python install` (reads `.python-version`)
     - `uv sync --locked`
   - jobs:
     - **data-lint**
       - `uv run taplo fmt --check`
       - on PRs: `uv run build-sdm validate --base-ref origin/${{ github.base_ref }}`
       - on push: `--base-ref ${{ github.event.before }}`, so every pushed commit is covered, not just the last one (F6)
       - if the push has no usable previous commit (the all-zero SHA, or a commit missing after a force push): `--base-ref HEAD`, with a warning. Not "no base": without a base every existing violation is an error, so the job would always fail. Against `HEAD`, structure is still checked and violations are warnings.
       - on dispatch: `--base-ref $(git merge-base HEAD origin/main)`; on `main` itself, where that is `HEAD`, `--base-ref HEAD~1`
     - **generated-fresh**
       - `uv run build-sdm check-generated`
       - on failure, a step copies the `check-generated` report to `$GITHUB_STEP_SUMMARY`. The report already lists the changed, stale and missing files and the fix: the build, a `git rm` for each stale file, and the commit.
     - **python-qa**
       - `uv run ruff check`
       - `uv run ruff format --check`
       - `uv run mypy` (`pyproject.toml` sets the files: `tools/build_sdm` and `tests`)
       - `uv run pytest`
3. Pin third-party actions to a major version, or to a SHA if org policy requires it:
   `actions/checkout@v7`, and `astral-sh/setup-uv@v10.3.3`. setup-uv publishes no major-version tag after `v7`,
   so it takes an exact version; Illuminate's `ci.yml` pins `v8.2.0` the same way.
4. Use stable job names, so the governance proposal (PR 5) can list them as required checks.
5. `AGENTS.md`: add a short "CI" section listing the jobs and the local command that reproduces each one.
6. Plan status: set `docs/plans/sdm-migration/04-ci.md` to `Status: done` and mark PR 4 done in the `README.md` status table.

## Verification
The workflow only triggers on PRs targeting `main`. For `pull_request` events, GitHub uses the workflow file from the PR's merge ref, so the new workflow runs on PRs into `main` before PR 4 merges.

- clean case: PR 4 itself, which targets `main`; all jobs green

For the failure cases, open throwaway PRs **targeting `main`** from branches based on `migration/04-ci`. Close them without merging:
- one generated file hand-edited: generated-fresh fails, with the fix shown in the summary
- a new subcategory with a bad name: data-lint fails with an `::error` annotation on the file

Also confirm that on PR 4 (the clean case), the warnings for existing violations show up as annotations but don't fail the job.
